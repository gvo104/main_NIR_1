# План НИР: стратегии поиска прогностических моделей в LLM-агентных системах

**Статус:** рабочий план по согласованной презентации; окончательные настройки эксперимента определяются после технического пилота и обсуждения с научным руководителем.  
**Область применения:** автоматизированное построение моделей эпидемиологического прогнозирования.  
**Основные источники:** [Google ERA — эпидемиологическое исследование](https://arxiv.org/abs/2605.16238), [методологическая статья ERA](https://arxiv.org/abs/2509.06503), [исследование стратегий поиска ML-агентов (AIRA)](https://arxiv.org/abs/2507.02554).

# Часть I. Общий план исследования

## 1. Название, идея и границы работы

**Рабочая тема:** «Исследование стратегий поиска оптимальных прогностических моделей в LLM-агентных системах».

В системе **ERA** языковая модель создаёт и изменяет исполняемый Python-код прогностических моделей. Каждый новый вариант возникает из ранее созданной программы; варианты и связи между ними образуют дерево. Поисковый алгоритм **FUTS/PUCT** на каждой итерации выбирает **одну уже существующую модель**, которую LLM должна попробовать улучшить. После исполнения новой программы её качество оценивается, а кандидат добавляется в дерево.

**Предмет нашего исследования — не качество одной конкретной LLM, не новая функция оценки и не ансамблирование прогнозов, а выбор родительского кандидата для следующей генерации.**

Исследовательский вопрос: **как организовать поиск по дереву программ, чтобы за ограниченное число попыток обнаружить наиболее качественную прогностическую модель?**

## 2. Цель, гипотезы и научная ценность

**Цель:** установить, как поисковая стратегия, доступный бюджет и свойства дерева кандидатов влияют на качество лучшей найденной модели.

Проверяемые гипотезы:

- **H1 — роль структуры дерева.** Если качество родительской модели хорошо связано с качеством её продолжений, жадный поиск может быть эффективен; при слабой связи исследование альтернативных ветвей может приносить больше пользы.
- **H2 — роль бюджета.** Относительная эффективность Greedy, ε-greedy и FUTS/PUCT может изменяться при увеличении количества допустимых попыток.
- **H3 — цена сложности.** Более сложная стратегия не обязательно превосходит простую при малом бюджете; важны и качество выбранной модели, и фактические затраты.

**Научная ценность:** не составить универсальный рейтинг алгоритмов, а выявить условия, в которых определённые политики поиска работают лучше или хуже, на примере деревьев моделей эпидемиологического прогнозирования. Аналогичные стратегии уже сравнивались в исследованиях ML-агентов; потенциальная новизна — анализ зависимости результатов от свойств дерева и конечного бюджета.

## 3. Формализация задачи

- Вершина `v` — конкретная версия Python-программы с её кодом, идентификатором, родителем и результатом валидации.
- Одно действие — выбрать доступную родительскую вершину, получить **одно** продолжение её кода и раскрыть результат проверки.
- Бюджет `B` — количество попыток генерации/раскрытия кандидатов. Ошибочные и неисполняемые варианты **тоже расходуют попытку**.
- Алгоритм видит только уже раскрытые кандидаты и известные по ним оценки; значения качества ещё не раскрытых программ скрыты.
- **Цель:** получить минимальную валидационную ошибку среди найденных к моменту `B` моделей: `min_{v ∈ S_B} L_val(v)`. Для FUTS, который максимизирует `score`, ошибка преобразуется в согласованную полезность, например `score = -L_val`.
- Итоговый выбор делается по валидации; **качество выбранной модели на отдельном тестовом периоде** служит независимой проверкой обобщения.

Для фиксированного дерева дополнительно можно вычислить **oracle gap**: разницу между ошибкой лучшей раскрытой модели и наилучшей ошибкой среди *всех* узлов данного дерева. Oracle не доступен поисковому алгоритму — только исследователю после эксперимента.

## 4. План экспериментов

### Этап 0. Предварительная техническая проверка существующих модулей

Проверить, что можно переиспользовать из Google ERA и AIDE без существенных изменений, какие возможности есть у локальной LLM или OpenRouter, насколько доступны средства исполнения и логирования. **Детальный протокол — во второй части документа.**

**Результат:** выбор базового агентного контура и подтверждение, что можно генерировать, оценивать и сохранять версии моделей.

### Этап 1. Постановка небольшой задачи прогнозирования

- Выбрать открытые исторические данные, предпочтительно [CDC FluSight](https://github.com/cdcepi/FluSight-forecast-hub) (или альтернативный подходящий ряд).
- Начать с одного выбранного ряда и одного прогнозного горизонта; дополнительные регионы/сезоны — после пилота.
- Зафиксировать входные данные, допустимые библиотеки, интерфейс программы и единую метрику. Для простого точечного прогноза подойдёт MAE; для вероятностного формата, близкого к ERA, — WIS/log WIS. **В пределах основного сравнения метрика не меняется.**
- Сделать хронологическое разделение: обучение → rolling-origin validation → отложенный тест. Избежать использования будущих значений и пересмотренных данных там, где они создают утечку.
- Подготовить простой независимый baseline, например прогноз последним значением или сезонным аналогом.

**Результат:** воспроизводимая задача, на которой любое решение можно оценить по одинаковым правилам.

### Этап 2. Генерация фиксированных деревьев кандидатов

- Коротко сравнить **Gemini 2.5 Flash**, **Gemini 3 Flash** (OpenRouter — если есть доступ) и локальную **Qwen Coder** по исполняемости кода, корректности интерфейса и стоимости одной генерации; выбрать **один** генератор для основных экспериментов.
- Использовать одинаковый шаблон промпта изменения кода. Наиболее близкий к ERA вариант — LLM получает задачу, код **одного выбранного родителя** и его валидационный результат.
- Создать несколько независимых деревьев ограниченной глубины/ветвления. **Пилот:** одно небольшое дерево; **рабочий ориентир:** несколько деревьев с ветвлением до 3 и глубиной около 3, без обязательства полностью заполнять большие деревья.
- Для каждой генерации сохранить `node_id`, `parent_id`, код, модель/параметры генератора, статус исполнения, оценку, время и текст ошибки при неудаче.
- После генерации **зафиксировать** деревья. Для каждого родителя задать воспроизводимый порядок раскрытия его продолжений; поисковая политика не знает кода и метрики ещё не открытых продолжений.

**Ограничение:** фиксированное дерево — контролируемая модель поиска, но не полная копия динамического агента: будущие ответы LLM не учитывают всю историю действий исследуемой стратегии.

### Этап 3. Сравнение поисковых политик

Основные стратегии:

| Стратегия | Принцип |
|---|---|
| Random | Равновероятный выбор доступного родителя для следующего раскрытия |
| Greedy | Выбор доступного родителя с лучшим известным качеством |
| ε-greedy | Обычно Greedy, с вероятностью `ε` — случайное исследование |
| FUTS/PUCT (ERA) | Выбор вершины с учётом ранга её качества и бонуса за менее исследованное поддерево |

**Правила честного сравнения:** одинаковые деревья и метрики, общий бюджет, одинаковые правила допустимых действий и обработки ошибок, скрытые оценки непосещённых узлов. Если у родителя закончились заранее сформированные продолжения, он исключается из множества доступных для расширения; это требуется явно реализовать в offline-симуляторе.

Начальные бюджеты: **5, 10 и 20 раскрытий**; они ориентировочные и могут меняться по итогам пилота. Основные прогоны выполняются на **нескольких независимых деревьях**, а не только с разными seed на одном дереве.

### Этап 4. Оценка и интерпретация результатов

**Основные показатели:**

1. Лучшая валидационная ошибка после каждого числа попыток (*best-so-far curve*).
2. Качество выбранной модели на независимом тестовом периоде.
3. Oracle gap на зафиксированном дереве.
4. Частота неуспешных кандидатов, реальное время исполнения и при возможности затраты на LLM.
5. Устойчивость результатов по независимым деревьям: медианы, разброс, доверительные интервалы при достаточном числе задач.

**Объясняющие характеристики дерева:** связь качества родителей и потомков, распределение величины улучшения, глубина расположения лучших решений, доля исполняемых кандидатов.

**Ключевые вопросы для выводов:** когда хватает Greedy, когда нужна более активная exploration-стратегия, как меняется сравнительная эффективность при росте бюджета и какие свойства дерева связаны с этим изменением. Отсутствие значимого преимущества FUTS — допустимый исследовательский результат.

### Этап 5. Расширение при наличии ресурсов

Проверить две наиболее показательные политики в **живом цикле LLM-генерации**, когда кандидаты создаются по мере поиска. Это даст предварительную оценку переноса результатов из фиксированных деревьев в реальную агентную систему. Возможное дополнительное направление — бюджетно-адаптивная ε-greedy; разработка нового алгоритма **не является обязательным результатом НИР**.

## 5. Минимальный и расширенный результат

| | Минимальный объём | Расширенный объём |
|---|---|---|
| Код | Работающий модуль выбора родителя и offline-симулятор | Подключение к реальному LLM-циклу |
| Данные | Одна воспроизводимая задача | Дополнительные сезоны/регионы |
| Деревья | Несколько независимых небольших деревьев | Больше деревьев, иные глубины/ветвления |
| Сравнение | Random, Greedy, ε-greedy, FUTS/PUCT | Дополнительные бюджеты и стратегии |
| Анализ | Кривые качества, разброс, oracle gap | Связь эффективности со структурой, online-проверка |

**Минимальный законченный научный результат:** корректное и воспроизводимое сравнение четырёх стратегий на фиксированных деревьях с оговорёнными пределами применимости выводов.

## 6. Риски и решения

| Риск | Как снижаем |
|---|---|
| Слабая или нестабильная генерация локальной LLM | Небольшой предварительный тест нескольких моделей, фиксация выбранной конфигурации |
| Дорогая генерация полного дерева | Пилот малой глубины, ограничения на ветвление, сохранение и повторное использование результатов |
| Неравные условия для алгоритмов | Единый интерфейс, одинаковые раскрытия, скрытые оценки, учёт неудач |
| Переобучение на валидации | Отдельный хронологический тестовый период; не использовать его для выбора ветвей |
| Недостаточно независимых экспериментов | Несколько исходных деревьев; не выдавать много seed на одном дереве за независимые задачи |
| Ограниченная переносимость offline-результатов | Явно ограничить выводы фиксированными деревьями; при возможности выполнить online-проверку |
| Опасный сгенерированный код | Выполнять только в изолированной среде с лимитами времени/памяти, без секретов и лишнего доступа к сети |

## 11. Проверка A — FUTS без LLM и без эпидемиологических данных

**Проверяемый модуль:** `era/implementation/futs.py`.

**Идея:** вместо LLM передать предсказуемую `generate_fn`, а вместо реального обучения — простую детерминированную `execute_fn`. Выполнить 10–20 итераций и записывать пары «родитель → потомок».

**Минимальный тест:**

```python
# Запускать из каталога era/implementation/
from futs import Problem, Solution, search

edges = []

def generate_fn(problem, parent_solution, parent_score):
    child = Solution(program=parent_solution.program + ">")
    edges.append((parent_solution.program, child.program))
    return child

def execute_fn(problem, solution):
    return float(solution.program.count(">"))  # чем глубже цепочка, тем выше оценка

best, score = search(
    problem=Problem(description="FUTS smoke test"),
    initial_solution=Solution(program="root"),
    initial_score=0.0,
    generate_fn=generate_fn,
    execute_fn=execute_fn,
    num_iterations=10,
    c_puct=1.0,
)

assert len(edges) == 10
assert score >= 1.0
print("Best:", best.program, score)
print("Edges:", edges)
```

**Что подтвердить:** импорт успешен; число созданных узлов соответствует бюджету; возвращается лучшая оценка; родители выбираются не произвольным внешним кодом, а внутренней политикой FUTS. Дополнительно просмотреть, как хранятся `Node`, `parent_index`, `num_visits`, `rank_score`, `puct`.

**Важно:** публичная функция `search()` возвращает лучшее решение и его оценку, **не полную историю дерева**. Для нашей НИР журнал узлов и выборов нужно будет сохранять отдельно либо сделать небольшую инструментальную обвязку. Это одна из потенциальных доработок.

**Критерий успеха:** воспроизводимый запуск без API, корректное число итераций, понятный интерфейс политики. Если тест не проходит, зафиксировать точный traceback и commit; не переходить сразу к переписыванию алгоритма.

## 12. Проверка B — AIDE как готовый агентный контур

**Проверяемый модуль:** [AIDE ML](https://github.com/WecoAI/aideml), прежде всего `aide/agent.py` и связанный журнал решений.

1. В отдельном окружении выполнить установку в режиме разработки: `python -m pip install -e .` из корня `aideml`.
2. Запустить короткую демонстрационную задачу репозитория (например, **house prices**) на **2–3 шага**, не подключая пока FluSight.
3. Выбрать один реально доступный генератор — локальную Qwen через OpenAI-совместимый endpoint/Ollama либо модель через поддерживаемый провайдер. **Для полностью локального прогона отдельно настроить и кодовую, и feedback-модель**, иначе часть вызовов может уйти во внешний API.
4. Сгенерированный Python-код исполнять в ограниченном окружении; проверить, что не предоставлены секреты, лишние права и доступ к пользовательским файлам.
5. Убедиться, что появились код хотя бы одного решения, результат валидации/ошибка, журнал итераций и визуализация дерева (если эти артефакты предусмотрены текущей версией).

**Что записать:** версии моделей, число попыток, успешных исполнений и ошибок, время/токены при наличии, файлы артефактов, корректность связей между кандидатами.

**Если не проходит:** разделить причины на `установка`, `доступ к LLM`, `формат ответа LLM`, `ошибка исполнения`, `ошибка разбора оценки`, `логирование`. Не путать проблемы LLM с неисправностью поиска.

**Критерий успеха:** минимальный сквозной цикл без ручного переписывания сгенерированного кода.

## 13. Проверка C — можно ли заменить политику поиска в AIDE

Просмотреть метод `Agent.search_policy()` и структуру `Journal`. В текущей открытой реализации политика выбирает между созданием новой программы (`None`), отладкой неуспешного кандидата и улучшением лучшего известного решения.

**Проверить на маленьком тесте:**

- можно ли выбрать произвольный уже существующий пригодный узел вместо `get_best_node()`;
- сохраняется ли корректная связь `parent → child` после такой замены;
- не ломаются ли операторы генерации, исполнения, отладки и логирования;
- возможно ли независимо задавать поведение Draft/Debug, чтобы при будущем сравнении политик оно было общим для всех.

**Критерий успеха:** тестовая политика случайного выбора родителя работает без переписывания генератора и среды исполнения. На этом этапе **не нужно интегрировать весь FUTS в AIDE**.

## 14. Проверка D — готовность интерфейса генератора

Короткий предварительный тест одного и того же задания на доступных моделях:

- Gemini 2.5 Flash и Gemini 3 Flash через OpenRouter, если есть ключ и подходящие модельные ID;
- локальная Qwen Coder, если хватает памяти/GPU.

Проверить: корректность формата Python-программы, её исполняемость, соблюдение интерфейса, способность внести изменение в код родителя, приблизительную стоимость и задержку. **Не превращать этот тест в самостоятельное сравнение LLM**: выбрать одну подходящую модель для дальнейшей работы.

Если доступно только одно решение, достаточно проверить его; отсутствие платного API не должно блокировать тест FUTS и анализ архитектуры AIDE.

## 15. Матрица первичной проверки

| Проверка | Успех означает | Выходной артефакт |
|---|---|---|
| Репозитории доступны и устанавливаются | Можно повторить окружение | Commit SHA, версии, лог установки |
| FUTS без LLM | Поиск и выбор родителя работают отдельно | Лог 10–20 шагов, `edges`, `best score` |
| AIDE с LLM | Работает генерация → исполнение → оценка | Сгенерированный `.py`, метрики, ошибки |
| Журнал AIDE | Сохраняются код, родители, оценки | Journal/HTML-дерево или его эквивалент |
| Подмена `search_policy()` | Поиск можно изолированно заменить | Минимальный patch/описание API |
| Безопасность исполнения | Код запускается с ограничениями | Записанные настройки sandbox |
| Доступный генератор | Есть хотя бы одна практически пригодная LLM | Краткая таблица теста моделей |

Статус каждой проверки: **PASS / PARTIAL / BLOCKED**, с указанием причины и следующего действия.

## 16. Решение по итогам этапа 0

**Вариант A — взять AIDE как основную систему**, если генерация, исполнение и журнал работают, а `search_policy()` заменяется точечно. Оригинальный FUTS из ERA использовать как эталон алгоритма/источник кода.

**Вариант B — взять FUTS/ERA и написать небольшую собственную обвязку**, если главная задача — offline-сравнение, а интеграция AIDE оказывается существенно сложнее, чем самостоятельный симулятор фиксированных деревьев.

**Вариант C — ограничиться контролируемым offline-симулятором**, если нет подходящей LLM или безопасной среды исполнения. Это допустимый резерв для проверки поисковых политик, но его результаты не следует выдавать за проверку полноценного агентного цикла.

**Результат этапа 0:** короткий `smoke_results.md` с матрицей проверок, списком переиспользуемых компонентов, блокерами и зафиксированным решением, на какой базе строится основной эксперимент.
